# 実装問題ワークフロー

業務志向の実装問題では「要件を漏れなく実装に落とし込めるか」「保守性の高い設計か」「エッジケースへの対応」が評価される。正解を出すだけでは不十分で、チーム開発を意識したコードが求められる。時間は十分にあるので、急がず以下の工程を全て踏む。

## Step 1: 仕様の完全分解

問題文を読み、以下の形式で要件表を作成してユーザーに提示する:

```
| ID | 要件 | 入力条件 | 期待される挙動 | 曖昧な点 |
```

- 仕様書の**全文**を要件表に反映する。1文も読み飛ばさない
- 「〜の場合は」「ただし」「なお」で始まる文は例外仕様の可能性が高い。個別のIDを振る
- 数値の丸め方、順序の安定性、同値の扱い、エラー時の出力形式など、細部を明記する
- 曖昧な点は解釈を決め、その根拠をコメントに残す方針とする

引っ掛け要素が意図的に仕込まれている前提で読むこと。

## Step 2: データモデルと設計

実装前に以下を決め、簡潔な設計メモを書く:

1. **中心となるエンティティ**と、その状態遷移
2. **モジュール/クラス分割**: 責務ごとに分ける
   - 入出力（パース、フォーマット）
   - ドメインロジック（仕様の中核）
   - エントリポイント
3. **拡張ポイント**: 「仕様が追加されたらどこを変えるか」を意識した構造にする

過剰設計は避ける。目安として、クラスは状態と振る舞いが結びつく場合のみ導入し、単なる手続きは関数で書く。

## Step 3: 段階的実装

要件表の ID 順ではなく、以下の順で実装する:

1. 入出力の骨格（サンプル入力を読み、ダミー出力を出す）
2. 正常系の主要フロー
3. 例外仕様・エッジケース
4. リファクタリング

各段階の完了時にサンプルで動作確認する。python-code-quality スキルの規約に従う。

## Step 4: テスト

edge-case-testing スキルを使用する。実装問題では特に:

- 要件表の各 ID に対応するテストケースを最低1つ作る（トレーサビリティ）
- 提出形式がスクリプト単体の場合でも、開発中は pytest でテストを書き、提出物に含められるなら含める

## Step 5: 文書化

提出物に以下を含める（形式が許す範囲で）:

- モジュール冒頭の docstring: 設計方針の要約（3〜10行）
- 主要な判断のコメント: 「なぜこの構造/アルゴリズムを選んだか」
- 曖昧な仕様に対する解釈とその根拠

採点者は「どのようにアプローチして解決に導いたか」を見る。コードから設計意図が読み取れる状態にする。

## Step 6: 提出前レビュー

- [ ] 要件表の全 ID がテストで検証済みか
- [ ] サンプル入出力が完全一致するか（空白・改行・順序）
- [ ] デッドコード、デバッグ用 print、未使用 import が残っていないか
- [ ] 命名が仕様の用語と一致しているか（仕様が「注文」なら `order`、勝手な言い換えをしない）
- [ ] README や docstring に設計意図が書かれているか
- [ ] ファイル構成・提出形式が指示通りか
